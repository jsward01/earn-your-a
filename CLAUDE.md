Guidance for Claude Code when working on Earn Your A.

## What This Is

A student accountability and rewards app built for Jonathan's family. His high-school-age daughter (Susana) struggles with organization; the app tracks her assignments, ties her allowance to grades/completion per house rules, and gives Jonathan (and his wife) a parent dashboard to monitor and approve payouts. Long-term goal: validate on personal use, then possibly open up to other families (schema is already family-scoped for this reason — see Data Model below).

**Official name:** Earn Your A
**Domain:** earnyoura.com (Cloudflare-registered, live)
**Hosting:** Cloudflare Pages (git-integrated — pushes to `main` auto-deploy)
**Repo:** github.com/jsward01/earn-your-a
**Local path:** `~/earn-your-a` on CachyOS Linux
**Backend:** Cloudflare D1 (SQLite) via Pages Functions, chosen over Supabase to stay all-Cloudflare and avoid Supabase's free-tier auto-pause-after-inactivity behavior, which would be a bad fit for sporadic family use

## Data Model

A "family" (`families` table) is the tenant boundary: every other table carries `family_id`, and every query is scoped by it — this is what makes the later "sell to unrelated families" goal a non-issue rather than a migration. There is no direct parent↔student foreign key; a family is just "however many `users` rows share this `family_id`." A family can have any number of `role = 'student'` users. Which student a request is about is decided in one place, `resolveStudentId` in `functions/_lib/students.ts` (see "Multi-student families" below) — never read `?studentId=` directly in an endpoint. Reward settings (`reward_settings`) are still one row per **family**, so all kids in a family share the same amounts/holdback/schedule.

Any number of `role = 'parent'` users can share one `family_id`, and they all see identical live data (same assignments, balance, payouts, etc.) — that's how Jonathan's wife/ex-wife/her husband can all get their own login to the same student (see the family-admin note below). Exactly one parent per family is `is_admin = 1` — only that parent can add new parent accounts or reset another parent's password; any parent can still reset the student's password (see `functions/api/auth/reset-password.ts`).

**Schema at a glance** (migrations in `migrations/`, all applied to remote D1): `0001_init` (core tables), `0002_sessions`, `0003_admin_role` (`users.is_admin`), `0004_avatar` (`users.avatar`), `0005_assignment_history` (audit trail), `0006_assignment_payout` (`assignments.payout_id`), `0007_reward_custom_unit` (`reward_settings.custom_unit`), `0008_holdback_type` (`reward_settings.holdback_type`, `'amount'|'percent'`, default `'amount'`), `0009_quiz_and_penalties` (`reward_settings.quiz_reward` default 10, `assignment_penalty` 0, `quiz_penalty` 10, `test_penalty` 20), `0011_import_ignores` (grade-import items a parent chose to ignore; applied to remote Oct 5, 2026), `0012_rewards_start` (`users.rewards_start_date`, `assignments.history_only`; applied to remote Oct 5, 2026 — Susana backfilled to 2026-08-14, her earliest work; 0 of 89 items history; balance unchanged at $247), `0010_adjustments` (`reward_transactions.kind` — `'adjustment'` for manual entries, NULL for automatic rows — plus `created_by` and `payout_id`; applied to remote Oct 5, 2026), `0013_missing_penalty` (`reward_settings.missing_penalty`), `0014_email_sending` (`users.email_alerts_allowed` default 1, `families.timezone` default `'America/Denver'`, `email_log` table — see Done → "Email sending"; written Oct 13, 2026), `0015_excluded_classes` (classes a parent left out of grade imports, per student; applied Oct 15, 2026), `0016_track_only_classes` (`excluded_classes.mode` `'track'|'leave_out'`, `assignments.track_only`, `users.track_only_alerts`; applied Oct 20, 2026), `0017_ai_usage` (`ai_usage`: per family + family-local day + feature, a use count for the daily AI limits; applied Oct 21, 2026), `0018_ai_plans` (`ai_plans`: saved AI Planner plans, private to the student, with checked-off steps; applied Oct 21, 2026). Money is never a mutable column: a student's balance is `SUM(reward_transactions.amount)`, and `reward_transactions` rows tied to an assignment are re-derived only when type/status/grade change.

## Working on this project (deploy, verify, test)

Hard-won notes from Sep 2026 sessions — read before shipping anything.

- **A push to `main` is a production deploy** (Cloudflare Pages runs `npm run build`, which is `tsc -b && vite build`; tests are *not* part of it — run `npm test` yourself). Confirm it actually shipped: compare `curl -s https://earnyoura.com | grep -o 'assets/index-[^"]*js'` with `ls dist/assets` after a local build, and `npx wrangler pages deployment list --project-name earn-your-a` (a **Failure** row means production is still on the previous good build). To read a failed build's log, use the Cloudflare API tool: `GET /accounts/<id>/pages/projects/earn-your-a/deployments/<deployment-id>/history/logs`. Once a build succeeded but Cloudflare failed the final step with "Failed to publish your Function... Unknown internal error" — transient; the next push deployed fine. The API token can't retry a deployment (mutations return "Authentication error"), so retry = dashboard button or another push.
- **Migrations that the new code reads must be applied to remote D1 BEFORE pushing** — otherwise the affected endpoints 500 in production. The Claude Code classifier blocks `wrangler d1 migrations apply --remote` (and raw remote writes) even when the user approves in chat, so **Jonathan runs it himself**: at an *empty* prompt type `!` as the very first character, then `cd ~/earn-your-a && npx wrangler d1 migrations apply earn-your-a-db --remote`. (Pasting that text as a normal message does nothing.) Read-only remote queries (`d1 execute --remote --command "SELECT ..."`, `d1 migrations list --remote`) are allowed and are the way to verify afterward. Every migration so far is additive (new table/column), so applying early is safe while the old code is still live.
- **Local test recipe** (never touches production): `npm run build`; `npx wrangler d1 migrations apply earn-your-a-db --local`; seed a throwaway family with `wrangler d1 execute earn-your-a-db --local --file=<sql>` (insert `families`, `users`, and `sessions` rows directly — password hashes can be junk); `npx wrangler pages dev dist --port 8788` (let it pick up the binding from `wrangler.jsonc`; do **not** pass `--d1`, which creates an empty second database); in the browser set `document.cookie = "session=<id>; path=/"` on localhost and reload; exercise endpoints with `curl`/python and the UI with claude-in-chrome; then tear down in FK-safe order (ai_plans, ai_usage, email_log, import_ignores, notification_settings, sessions, assignment_history, savings_goals (no `family_id` column — delete by `student_id`), reward_transactions, assignments, payout_requests, reward_settings, users, families). The local DB keeps 2 users / 1 family from earlier sessions — leave those. Since Sep 21 it also holds a "Campus Test Family" (see Done → Overview) — leave that too. Stop the server with `pkill -f "[w]rangler pages dev"` (the bracket trick matters: a plain pattern also matches the shell running the command and kills it).
- **Browser checks on the live site:** Jonathan's Chrome may be logged in as *anyone* — check `/api/auth/me` before assuming who you are (it was Susana's session once). I can't log in (no passwords) and must not create real data on production; open-and-cancel modals is fine.
- **Ask before every push**, even after a migration was applied: Jonathan approves each push explicitly ("Yes, push it"), and he is often away right after — don't deploy something unattended on inference.
- **Commit hygiene:** chain a commit after a doc-editing script with `&&` (or check the script's output first). Once a failed docs script was followed by an unconditional `git commit`, committing stale docs; it was caught and amended before pushing.
- **UI preference:** pop-ups should be centered in the viewport (max-width, scrollable), not bottom sheets — Jonathan has asked for this on several modals. The older bottom-sheet modals (payout, savings goal, password reset, login "forgot password") are still to be converted.

## Locked-In House Rules (business logic — confirm with Jonathan before changing any default)

- **Regular assignments:** $3 if on time and ≥70%. Late/missing/<70% = $0 (the below-passing penalty is configurable, default $0).
- **Quizzes:** ≥70% = +$10. <70% = -$10 (penalty configurable).
- **Tests:** ≥70% = +$20. <70% = -$20 (penalty configurable). Changed Sep 22, 2026 from "tests & quizzes both $20" at Nicole's suggestion; reward and penalty amounts are separate settings.
- **Every rule is a parent setting (Jonathan, Oct 8 2026):** new rules and student-facing features get a Settings switch/field whose default is the current behavior. Today's defaults below are Susana's house rules, not hardcoded behavior.
- **Missing work** earns $0 and costs nothing by default; Settings → "Penalize missing work" makes it cost the failing-grade penalty for its type.
- **1-week makeup window** (Settings → "Allow retakes", 0 days = off) on any missing/low assignment or test/quiz — retake within the week and score ≥70% reverses the penalty. After 1 week, the penalty locks in permanently.
- **Holdback buffer** (~$20) held back on payout requests to cover upcoming penalties; negative balances carry forward.
- **Reward type is configurable** (money/screen-time/points/custom), not hardcoded to dollars.
- Implementation lives in **two places that must agree**: `src/lib/rewards.ts` (`getRewardStatus` — what the UI shows, amounts hardcoded) and `functions/_lib/rewards.ts` (`computeAssignmentReward` — what the ledger records, driven by the family's settings). Makeup-window state is `nextMakeupState` in `functions/_lib/assignments.ts`.
- **Tests:** `npm test` (Vitest, ~0.2s; not part of the Pages build, so a failing test never blocks a deploy — run it yourself before pushing reward changes). 728 tests (Oct 15) — incl. `functions/_lib/emailAlerts.test.ts`, `functions/_lib/notificationSettings.test.ts`; `src/lib/import/import.test.ts` (grade import parser + matching), `functions/_lib/adjustments.test.ts` (adjustment validation), `functions/_lib/rewards.test.ts` (ledger rules incl. thresholds/boundaries/custom settings, per-type rewards and penalties, holdback math), `functions/_lib/assignments.test.ts` (makeup window), `src/lib/rewards.test.ts` (UI labels), `functions/_lib/rewards.parity.test.ts` (browser vs. ledger must give the same number for every type × grade). The parity test lives under `functions/` on purpose — importing a `functions/` file from `src/` pulls Cloudflare types into the browser build and breaks `tsc -b`. Sanity-checked by mutation (flipping `>=` to `>` fails 7 tests; changing the UI's test reward fails 10).
